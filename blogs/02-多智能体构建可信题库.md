# 用多智能体从官方文档生成"可信"题库：生成、校验与三次返工实录

> 让 AI 出 344 道题只花了几分钟，让这些题"可信"花了一整条流水线——10 个代理分主题出题（强制填出处）、15 个代理逐题对抗校验（wrong 必须引用原文）。中间经历了 API 限流崩流、工作流缓存丢失两次工程事故，以及一处真实的知识性纠错（PID 回路数 8→16 的固件版本冲突）。文末是可直接复用的流程模板。

## 〇、问题定义

"可信"拆开是三层：

1. **格式可信**——每道题都是合法结构（选项数量、答案字母在范围内）
2. **内容可信**——答案与官方文档一致，且能指出在哪份文档的哪一章
3. **可追溯**——低置信的答案要能被识别出来，而不是混在高置信答案里装作一样

单次生成只能保证第一层。第二、三层需要**生成与校验分离**——而且校验方不能看到生成方的结论。

## 一、素材：从 CHM 和 PDF 里挖文本

西门子的官方资料格式很"古典"：

| 资料 | 格式 | 提取方式 | 产出 |
|---|---|---|---|
| 技术参考 PLUS 2.6 | CHM 72MB | `hh.exe -decompile` 反编译 → HTML → Python 剥标签 | 261 篇 FAQ |
| Micro/WIN SMART 帮助 | CHM 15MB | 同上 | 661 篇指令文档 |
| 系统手册 V2.8 | PDF 1130 页 | pypdf 按章切分 | 12 个章节文件 |
| 选型手册 V2.8 | PDF 40 页 | pypdf | 全文 |

两个坑值得记：

- **中文路径带括号会让 `hh.exe -decompile` 静默失败**——`S7-200 SMART 技术参考(PLUS 2.6).chm` 反编译产出 0 个文件且不报错。复制到纯 ASCII 路径重跑即好。命令行工具对非 ASCII 路径的容错，永远比想象中差
- 部分课程 PDF 是 **AES 加密**的（能正常打开阅读，但提取时报 `cryptography>=3.1 is required`）——`pip install cryptography` 之后 pypdf 就能解。这类"所有者密码"加密在国内资料里很常见

## 二、出题：10 个代理并行，按主题切分

没有把 1.5MB 手册一股脑塞给一个模型，而是**按考点主题切给 10 个代理**：硬件选型 / 数字量模拟量 IO / 存储寻址 / 基本指令 / 高速计数 / 运动控制 / PID / 串口通信 / 以太网通信 / HMI 软件维护。

每个代理拿到的东西：

- **指定资料路径**（不是全文，是该主题对应的章节和 FAQ 文档）
- **统一输出 schema**：每行一个 JSON

```json
{"topic":"PID控制","type":"single","q":"S7-200 SMART CPU 最多可以支持多少个 PID 控制回路？",
 "options":["A、4","B、8","C、16","D、无限制"],"answer":"C",
 "explain":"系统手册V2.8第9.9节：十六条PID指令，LOOP操作数0~15","source":"系统手册v2.8第13章"}
```

- **三条硬规则**：答案必须以资料原文为依据、没把握的知识点不出、不出看图题

`source` 字段是反编造的关键——出题者被迫回答"这个答案你从哪知道的"，编造的成本瞬间变高。

产出 346 题，difflib 相似度去重后 344 题。

## 三、事故一：15 个并发代理触发 API 限流

校验阶段的设计：10 个代理逐题核对题库答案 + 5 个代理为 5 套模拟卷 350 题补答案，共 15 个高推理度代理并发——**429 限流，1 个代理被拒，工作流脚本对 null 结果没保护，`v.results` 直接崩了整条流水线**。

修复两手，之后成了所有工作流脚本的固定写法：

```javascript
// 1. 分批调度：每批 3 个并发，失败的批末尾统一重试
async function runBatched(jobs, size = 3) {
  const out = new Array(jobs.length).fill(null)
  for (let i = 0; i < jobs.length; i += size) {
    const res = await parallel(jobs.slice(i, i + size).map(j => () => j()))
    res.forEach((r, k) => { out[i + k] = r })
  }
  return out
}
// 2. 每个回调 null 安全 + 聚合处 filter(Boolean)
agent(prompt, opts).then(v => v?.results ? {...} : null)
```

教训排序：**null 保护 > 分批 > 重试**。没有 null 保护，任何一个代理失败都会把整条流水线带崩；有了它，分批和重试只是优化。

## 四、事故二：journal 落盘丢失

更诡异的一集：工作流明明显示 7/7 代理完成，结果文件（journal）里只有 2 条。另外 5 个代理的结果去哪了？

排查出两条恢复路径，都值得记住：

**路径 A：从代理 transcript 里挖。** 每个代理的 JSONL 转写里有它最终的结构化输出（StructuredOutput 工具调用）。写个递归提取器，按特征字段（`items[].name`）在转写里定位最终结果：

```python
def dig(o):
    if isinstance(o, dict):
        if 'items' in o and isinstance(o.get('items'), list) and 'name' in o['items'][0]:
            return o['items']
        for v in o.values():
            r = dig(v)
            if r: return r
```

**路径 B：Workflow 的 resumeFromRunId。** 缓存按 `(prompt, opts)` 精确命中——进了 journal 的代理秒回缓存，没进的自动重跑。停掉旧任务 → resume → 缺失的 3 个代理补跑，一次成功。

结论：**执行框架的持久层不可信时，产物要尽早落成自己的文件**。后来所有代理都被要求"直接把结果写到目标文件"，journal 只当参考。

## 五、真正的收获：校验抓到了一处知识错误

15 个校验代理逐题核对（不是抽查，是全量 344+350 题），最有价值的发现：

> 题库里"PID 回路数量"按技术参考 PLUS 2.6 写了 **8 个**；但系统手册 V2.8 第 9.9 节明确写"可以在程序中使用十六条 PID 指令"、LOOP 操作数 0~15、向导"最多可组态 16 个回路"。**固件 V2.8 已扩展到 16 个**。校验判原答案错误，并附上原文证据。

有意思的是出题代理并没有"错"——它引用的旧版技术参考确实写着 8。**两份官方文档打架时，必须提前定好裁决规则**（本次的规则：以最新版系统手册为准），否则校验方无所适从。

这就是"生成-校验分离"的意义：出题代理和校验代理**互不知道对方的结论**，校验方被明确要求"wrong 必须引用原文关键句"。同一个模型，换个身份、换套约束，就能查出另一个实例的错——前提是两者的上下文隔离。

最终统计：344 题仅 1 处知识性错误（已修正）；350 道卷题答案全部补全——293 高置信 + 57 中置信 + **0 空缺**。而且置信度不是装饰字段：低置信题在产品里**进待复审队列、不参与判分**，用户看到的是明确的"答案整理中"，而不是一道可能错的题。

## 六、可复用的流程模板

```
资料提取（格式各异，全部脚本化，验证产出数量）
   ↓
按主题分派出题代理 ×N
   统一 JSON schema + source 字段 + 反编造三规则
   ↓
格式校验（schema assert）+ 相似度去重（difflib ≥0.88 视为重复）
   ↓
对抗校验代理 ×N（每题核对原文；wrong 必须给证据；版本冲突定裁决规则）
   ↓
修正应用 → 数据重建 → 回归测试
```

六个工程要点：

1. **按主题切分**而非按页切分——主题代理有完整语境，题目质量天差地别
2. **分批调度**（每批 2~3 个）防限流，全量 null 保护防崩流
3. **产物文件化**：代理直接写目标文件，不依赖框架缓存
4. **出处字段强制**：反编造的最廉价手段
5. **校验方与生成方上下文隔离 + 证据要求**
6. **置信度进产品逻辑**：AI 产物必须带着"我有多确定"的元数据流转
